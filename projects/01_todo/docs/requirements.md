# Todo：要件と段階

## 利用者と目的
自分の作業を忘れないため、短いTodoを登録し、完了と未完了を切り替える。
Stage A/Bは再起動で消える制約を画面に表示し、Stage Cで保存を実現する。

| 要件ID | 操作・条件 | 期待結果 |
| --- | --- | --- |
| TODO-01 | タイトル入力→追加 | 未完了のTodoが1件増える |
| TODO-02 | 一覧表示 | 新しい順、同時刻はID降順で安定して表示 |
| TODO-03 | 完了状態を切り替える | 対象のTodoだけ変わる |
| TODO-04 | タイトルを編集し保存 | 対象のタイトルだけ変わる |
| TODO-05 | 削除する | 対象が消え、件数に反映 |
| TODO-06 | 全件/未完了/完了を選ぶ | 条件に一致した一覧。総件数と未完了件数は全件を基にする |
| TODO-07 | 空白だけ・長すぎるタイトル | 追加・更新しない。入力の近くに理由を表示 |
| TODO-08 | APIが失敗 | 失敗を表示し、成功したように一覧を書き換えない |
| TODO-09 | Stage Cで再起動 | 保存した内容が残る |

タイトルは前後空白を除去後1〜100 Unicodeコードポイント。同名は許可し、IDで識別する。
結合文字や絵文字の見た目の文字数とは異なる。JSのlengthだけとは差があることを確認する。
入力の安全な表示はテキストとして行い、HTML文字列として挿入しない。

## Stage A：React内で動かす
ローカルstateで追加、一覧、切り替え、編集、削除、フィルターを実装する。
要件TODO-01〜07を確認する。再読み込みで消えることを明示する。
受け入れ条件を先に書き、1操作ずつ実装する。最初から全コンポーネントを生成しない。

## Stage B：FastAPIに接続
サーバー内メモリを一時保存先とし、1プロセス・1workerで学習する。
再起動時に消える制約を明記する。[API契約](api-contract.md)を守る。
通信中の二重送信防止、初期ロード、空一覧、失敗表示、再試行を設計する。
ローカル開発のCORSは実際のFrontend originだけに限定する。
要件TODO-08を追加確認する。

## Stage C：DBで保存
[データモデル](data-model.md)を実装し、API契約を保ったまま保存先を置き換える。
SQLiteで始めてもよい。PostgreSQLへの移行時は空の開発DBで型・制約・テストを再確認する。
既存データを残す移行は別作業として設計し、無断でDBを消さない。
要件TODO-09を確認する。

## 対象外
ログイン、共有、通知、期限、添付、一般公開は今回の必須範囲外。
これらを追加したい時は先に要件と前提をCoachと確認する。

## 学習者の設計提出
画面の状態、コンポーネントの責任、データの流れ、検証する入力、
失敗時の動作をdocs/design.mdへ本人が書く。完成コードは提出設計の代わりにならない。
