# Webアプリ開発学習環境：全体アーキテクチャ

設計版: 1.0
公式仕様確認日: 2026-10-05
対象: 学習者1人、VS Code + GitHub Copilot、GitHub Repository
段階: Step 3〜12のMVPファイルを実装済み。Copilot実機の受け入れ確認は未実施。

## 1. 採用する構成

教材・課題・実装・評価の根拠を1つのRepositoryに保存する。
learning-coachを学習の入口とし、5つの専門Agentを必要に応じて使う。
学習環境自体はMarkdownとCopilot設定で動作させ、専用サーバーや進捗DBを必要としない。

React / FastAPI / PostgreSQLは、学習者が作るアプリで使用する。
この区別により、初心者はアプリを起動できる前から学習を始められる。

学習者 → learning-coach → 教材 → 理解度チェック → 演習・実装
→ テスト → デバッグ → レビュー → learning-coachによる評価 → 次の課題

理解が不足していれば、補足説明 → 追加演習 → 再評価に戻る。

## 2. データの置き場所

| 場所 | 内容 |
| --- | --- |
| .github/ | 共通方針、6つのAgent、分野別Instructions、Prompts、Skills |
| curriculum/ | 前提知識・到達目標付きのMarkdown教材 |
| exercises/ | 難易度別の課題、学習者の回答・実装 |
| projects/ | Todo、CRUDアプリ、最終プロジェクトの仕様・設計・実装 |
| progress/ | 学習者情報、ロードマップ、確定評価、評価記録、履歴 |
| docs/ | 本設計書、運用方法、評価基準 |

チャット履歴だけを記憶として使わない。再開に必要な情報はファイルに残す。
教材・演習・評価・セッションには識別子を付け、相互参照できるようにする。
個人情報は最小限とし、パスワード、APIキー、接続情報はコミットしない。

## 3. Agentの責任

| Agent | 入力 | 出力と責任 |
| --- | --- | --- |
| learning-coach | progress、回答、実装、実行結果、専門Agentの報告 | 今日の課題、理解度確認、確定評価、progress更新 |
| curriculum-designer | 診断結果、目標、学習時間 | 前提関係・順序・難易度を含むロードマップ案 |
| lesson-author | 学習目標、前提知識、つまずき | 指定の14見出しを持つ教材 |
| exercise-designer | 学習目標、難易度、評価観点 | 目的・前提知識・課題・制約・ヒント・完了条件・チェックポイント・発展課題を持つ演習 |
| debugger | 期待、実際、エラー、再現手順 | 原因候補、調査手順、原因の根拠、再テストと再発防止の指導 |
| code-reviewer | 要件、差分、テスト結果 | 問題の位置・理由・影響・改善方向・確認方法 |

code-reviewerは正しさ、可読性、設計、保守性、型安全性、エラー処理、
セキュリティ、テスト、性能を確認する。対象外や確認できない観点は明示する。

progress内の5ファイルを最終決定・更新するAgentはlearning-coachだけとする。
curriculum-designerはロードマップ案を返し、Coachがroadmap.mdに反映する。
他Agentは教材や課題を作成できるが、採点結果を確定しない。
debuggerとcode-reviewerは原則として読み取りと助言を担当する。
学習者の解答・アプリ実装をAgentが無断で完成させない。

MVPは同時並行でAgentを動かさず、役割を順番に切り替える。
引き継ぎには「対象ID、目的、読んだファイル、観察事実、支援レベル、
未解決点、Coachへの提案」を含める。引き継ぎUIに依存せず、
Agentを手動選択して同じ情報を渡せる構成にする。

## 4. Copilot設定の役割

| 種類 | 用途 |
| --- | --- |
| copilot-instructions.md | 学習者主体、解答の制限、証拠に基づく評価などの共通原則 |
| agents/*.agent.md | 役割、作業手順、入力・出力、担当範囲 |
| instructions/*.instructions.md | applyToで対象ファイルに適用する分野別のルール |
| prompts/*.prompt.md | Localで使う定型依頼の互換入口 |
| skills/*/SKILL.md | 教材作成など、必要時に読み込む再利用手順 |

重要な学習方針を分野別Instructionsだけに置かない。
参照対象のファイルがまだない会話でも共通原則が伝わるようにする。
PromptはAgentのツール制約を不用意に上書きしない。
モデル名は固定せず、利用可能なモデルを選択できるようにする。

## 5. 学習セッション

1. Coachを選び「今日の学習を始めたい」と伝える。
2. Coachはprogressの5ファイルと未解決課題を読む。
3. 未診断なら経験・目標・学習時間を聞き、説明問題と小さな実技を出す。
4. 診断に合わせ、今日の目標と完了条件を1つずつ提示する。
5. 教材があれば案内し、不足する場合はlesson-authorで作成する。
6. 学習者が説明・予測を行ってから演習に進む。
7. 学習者が実装し、テスト結果と利用したAI支援を提出する。
8. 必要に応じてdebuggerとcode-reviewerを使う。
9. Coachが根拠を確認し、評価と次の課題を決めて記録する。

初回診断は未回答を不正解にせず「未評価」とする。
過去の経験の自己申告だけで高得点を付けず、短い実演で確認する。
学習時間や目標が未回答なら仮のロードマップと明記する。

## 6. AI支援と自立の評価

演習の難易度L1〜L5と、AI支援H1〜H5を別に記録する。

| 支援 | 内容 |
| --- | --- |
| H1 | 質問で考えを引き出す |
| H2 | 着目点を1つ提示する |
| H3 | 設計案や疑似コードを提示する |
| H4 | 必要最小限の部分コードを説明付きで提示する |
| H5 | 対象課題の完成例を説明付きで提示する |

通常はH1〜H3を使用する。まず学習者の予想・試行・つまずきを聞く。
行き詰まりや本人の要望に応じてH4〜H5へ進み、使った理由を記録する。
完成例を見た課題は、自力実装の証拠にしない。
別の類題でAIのヒント・生成・補完なしに再評価する。
自力評価でも公式資料の参照は許可し、参照内容を記録する。

教材中の小さな説明用コードと、演習の解答コードを区別する。
「このアプリ全部作って」と言われたら、要件の分割と最初の一歩を支援する。

## 7. 進捗モデル

Knowledgeは概念の説明、Practiceは実装・テスト・デバッグ、
Independentは支援なしで判断・応用する力として評価する。

共通尺度は0=未学習、1=用語を知る、2=説明があれば理解できる、
3=例を参考に実装できる、4=自力で実装できる、5=説明・レビューできる。
Knowledgeでは「実装できる」に対応する段階を、コードや設計理由の説明で確認する。
Independentでは利用した支援も確認し、H3の設計案で完成しただけなら4にしない。
3軸を同じ値にそろえたり、平均点だけで合否を決めたりしない。

初期値0は未評価フラグと併記し、能力がないと断定しない。
教材を読んだだけ、テストが通っただけでは習得扱いにしない。

| 状態 | 条件 |
| --- | --- |
| not_started | 学習未開始。未評価かどうかを別に表示 |
| learning | 学習中、または証拠が不足 |
| ready | 当該範囲で3軸すべて3以上かつ必須課題を満たす |
| independent | 3軸すべて4以上で、別の類題の自力実装・説明・デバッグを確認 |
| revisit | 再評価で不足が判明し、補強が必要 |

readyは前提単元として次へ進める目安であり、習得完了を意味しない。
最終プロジェクト完了時は主要スキルのindependentと、プロジェクトの完了条件を確認する。

各評価に、評価ID、セッションID、対象スキル・範囲、課題ID、
回答・成果物への参照、実行コマンドと結果、支援レベル、
変更前後の得点、理由、残る弱点、次の課題を残す。
未実行のテストは未実行、本人申告は本人申告と区別する。

progress.mdは現在の確定状態、assessments.mdは採点の根拠、
history.mdはセッション履歴、roadmap.mdは次の学習計画、
learner-profile.mdは目標・経験・制約を保持する。
同一評価IDの二重適用を避ける。更新が中断したら記録の整合を確認して再開する。
学習者は差分を確認してGitに記録し、誤更新を戻せるようにする。

## 8. カリキュラムの依存関係

基本順序はPhase 0〜14を採用する。
Web基礎にはHTML/CSS、アクセシビリティ、ブラウザー、HTTPを含める。
FastAPIの前にPython基礎の橋渡し教材を用意する。
DatabaseではSQL、制約、トランザクションを学び、PostgreSQLへ進む。

テストとデバッグは最初のコードから小さく導入し、
Phase 10・11で体系化する。Gitも初期から学習記録に使う。
DockerはPhase 12で仕組みを学ぶ。先にDB起動で使う場合は
操作手順を提供し、それだけでDocker習得としない。

Phase 14はprojects/final_projectを中心に進める。
診断に応じて既知の単元を短縮するが、前提スキルは実技で確認する。

## 9. 実践アプリの構成

React + TypeScript + Viteの画面
→ HTTP / JSON
→ FastAPI + PydanticのAPI
→ PostgreSQL

ブラウザーからDBへ直接接続しない。
入力検証・認証・認可はAPI側でも行う。
認証方式の詳細はPhase 9の仕様作成時に脅威と要件から選定する。

FrontendのテストはVitestとReact Testing Library、
Backendはpytestを使用する。
型確認、テスト、実行確認は別の検証として扱う。

TodoはReact内の状態管理から始め、次にFastAPI、最後にDB保存を追加する。
初期DBはSQLiteも許容するが、PostgreSQLへの移行時は差分を検証する。
CRUDアプリではPostgreSQLを使い、要件・DB・API・UI設計から実装まで経験する。
最終プロジェクトでは学習者がテーマを選び、認証・認可・テスト・Dockerを含めて完成させる。

## 10. 現行仕様と制約

公式資料により、custom agents、custom instructions、skillsを採用する。
AgentやSkillは別々の常駐サービスではなく、Copilotが読み込む役割・手順である。

- Prompt filesはAgent Hostでは読み込まれず、Localでは利用可能とされている。
  要求された6つのPromptは互換入口として残すが、必須経路にしない。
  定型処理は対応するSkillからも利用できるようにし、Agentへの自然文依頼も用意する。
- Handoffsは役割の切り替えを助ける機能として扱う。
  UIが使えない場合は手動選択と引き継ぎメモを使用する。
- Agentのtoolsや機能対応は実行環境に依存する。
  Step 3以降で対象環境の認識状態と利用可能なツールを確認する。
- Markdownによる「Coachのみ更新」は運用上の責任分離であり、
  ファイルごとの強制アクセス制御ではない。
  MVPは逐次実行・差分確認・履歴で管理する。
  厳密な強制が必要になったら、直接書き込み権限を分離し、
  認証された更新サービス経由で確定評価を更新する構成へ拡張する。
- AIの正答や指示遵守は保証されない。
  初回の受け入れ確認で支援の出しすぎ、採点の捏造、担当外更新を確認する。

公式仕様の確認と、この利用者のVS Codeでの動作確認は別である。
本Stepでは公式資料を確認したが、利用者環境でのAgent実行は未検証。

## 11. MVPの完成条件

6つのAgent、共通指示、分野別指示、6つのPrompt、
教材作成Skillと互換性を補うSkill、progressの5ファイル、
orientationとweb_basicsの具体教材、最初の演習、
Todo仕様、初回診断を用意する。

受け入れ確認:
1. Repositoryルートを開き、learning-coachを選択できる。
2. 新しい会話でも保存された進捗を読み、診断または学習再開ができる。
3. 「HTTPを学びたい」に対して完成コードより先に説明・予測を求める。
4. 「全部作って」に対して課題を分割し、H1〜H3から支援する。
5. debuggerとreviewerが修正版を無断で実装せず、理由と調査方法を返す。
6. 他Agentは評価案を返し、Coachだけが根拠付きで確定状態を更新する。
7. 未実行テストを成功扱いしない。
8. 理解不足なら追加演習へ戻り、AI生成物だけで自立認定しない。
9. Promptが読み込まれない環境でもAgentとSkillで学習を続けられる。

後から全教材、CIでの形式検証、Dev Container、学習ダッシュボード、
複数学習者対応を追加できる。MVPでこれらを必須にしない。
