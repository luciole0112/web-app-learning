# 自分の要件から小さな記録アプリを設計する

課題ID: WEB-006 / 難易度: L5 / 目安: 複数セッション / 通常の支援上限: H3

## 目的
曖昧な希望を実装可能な要件と完了条件にする。

## 前提知識
WEB-005相当の実装経験、Git、基本のテスト・デバッグ。Coachが前提を確認する。

## 課題
「毎日の小さな活動を記録したい」という希望から利用者と目的を決める。ユーザーストーリー3件、画面案、データ項目、受け入れ条件を先に書く。優先度の高い1つを実装し、テスト・デバッグ・レビューまで行う。

提出先：exercises/web/submissions/WEB-006/attempt-01/。
回答はanswer.md、実行・観察はevidence.md、必要なHTML/CSS/JSはsite/に保存します。
再提出はattempt-02以降へ保存します。本人が作成し、AIの文章を自分の説明として転記しません。

## 制約
スコープは追加・一覧・削除程度から開始する。永続化の有無を先に決め、未実装機能を完成扱いしない。認証が必要なら後続Phaseまで保留する。

## ヒント
読む前に自分の予想と試行を書き、開いた段階を記録します。
<details>
<summary>H1：必要になったら開く</summary>

誰が何をできると役立つか。

</details>

<details>
<summary>H2：必要になったら開く</summary>

要件を入力・操作・結果で書き、失敗条件も考える。

</details>

<details>
<summary>H3：必要になったら開く</summary>

1つのユーザーストーリーを画面から状態更新まで縦に完成させてから広げる。

</details>

## 完了条件
要件とテストの対応があり、本人が設計理由を説明する。未達条件と制約をREADMEに記載する。

## チェックポイント
要求変更を1つ受けて影響を説明できる。支援量を明記し、独立評価は別類題で行う。
実行した環境、手順、期待、実際、AI支援の最大レベルをevidence.mdに記録します。
Coachは対象範囲だけ採点し、[評価基準](../../../docs/assessment/rubric.md)を参照します。

## 発展課題
保存方式を変更する場合のデータ移行と失敗時の扱いを設計する。
